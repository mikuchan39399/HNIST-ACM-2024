# P04 SegGraph 最终对拍与整理 (2026-09-06)

起点为 c41a6c2。原套件只有 300 组最多 40 点/60 操作, 压缩图与朴素图都跑同一份
Dijkstra, Empty 只比点边数量, 未登记行为范围。本轮先补独立及目标规模验证再润色注释。

## 真实容量缺陷与裁决

旧构造仅按约 4 * max_n 分配点表, 新建中继却不受限, max_m 只影响边表。
在旧版运行 `SegGraph<LL> sg(1,200); sg.build(1);` 后循环 100 次
`int v=sg.add_p2new(1,1); sg.add_p2p(v,1,1);`, Linux ASan 报
heap-buffer-overflow, 位于 Graph::add 读取点状态, 调用来自 add_p2new。
现场 `.zoi-checks/codex-work/seggraph-capacity-probe.log`, 退出码 1。

用户确认采用独立中继预算: 第三参数 max_extra 默认 -1 表示 max_n,
r2r/r2new/p2new 各消耗一个, 分配按原点上限和中继预算分别计算, 新建中继处断言预算。
两参数调用保留, q 远大于 n 时显式传 q。build 检查非空原点容量并恢复每轮预算。
两棵树的儿子表只覆盖骨架, 从约 4N 缩到 3N, 不为中继点分配儿子表。
Graph 本身不改, 边数组仍允许扩容, 点表不自动扩容。

## 独立参照与规模

- 保留原 300 组随机测试; 新增种子 42 的 400 组最多 16 原点/32 操作,
  朴素矩阵逐点展开区间, 用户可见中继独立编号, Floyd 比全部原点及返回中继点的全点对。
  参照不包含线段树骨架, 不调用被测 Dijkstra。
- Empty 用实际 BFS 可达性比矩阵可达性; SCC 的业务点同分量当且仅当 Floyd 双向可达。
  核对六类接口、零权、自环重边、单点/完整/重叠区间、后续继续使用中继、骨架无免费路径。
- 默认 20 万原点/20 万操作, 完整区间双方向星、非对齐区间、逐点核对大图答案;
  20 万/1/2/199999/20 万重建, 32 点环块式 SCC 分组, 参照为闭式结构。
- 原点仅 1/2 个, 连续 20 万次造中继恰好用满预算, LL/Empty 均测,
  三类造点交错、重复 build、零中继预算及旧两参数构造。
- 固定样例覆盖 INF-1 的有效距离, 负权 DAG 用朴素反复松弛并比闭式答案,
  不把负权交给 Dijkstra。SCC/Dijkstra 只登记本轮组合范围, 不冒充其全接口验收。

## 验证顺序与结果

1. 修改注释前, Windows 新小暴力/20 万压力通过; 修复容量后跑完新增预算用例。
   Linux GCC 13.1 普通和 ASan/UBSan 在 8 MiB 栈下通过后, 才润色源码注释与 Usage。
2. 最终 Windows GCC 15.2 常规回归 23 套通过 (`.ci-results/p04-final`),
   随后仅 Usage 头文件说明变化, 再单独跑 seggraph 通过 (`.ci-results/p04-final-seggraph`)。
   runner 自动保存指纹和两层表; 整份登记 JSON 改动后的旧条目也得到刷新。
3. 最终 Linux 默认套件普通 PASS、ASan/UBSan PASS, 均默认 8 MiB 栈,
   实测运行约 0.73 秒/7.86 秒, 源码前后 stable=true。
   [专项原始摘要](stress/seggraph-20260906.json) 记录实际命令、参数、哈希与结果;
   它不是 runner 格式, 不导入 runs 目录。驱动与日志在库内 codex-work/p04-linux.py 和 .ci-results/p04-linux。
4. 从最终源码提取 Usage, 重复 include segGraph.h 并接 dij.h 编译运行,
   输出独立核对为 `0 3 8 7 7`。日志 `.zoi-checks/codex-work/p04-usage-*`。

现有指纹器会保守扫描注释里的 include, 曾把 Usage 的短名头当相对依赖而报缺文件;
因此 Usage 用普通注释说明所需短名头, 真实题目提取时再加 include, 最终验证重新执行。
这是存证扫描的现有限制, 不是算法故障, 本轮不改全库指纹规则。
