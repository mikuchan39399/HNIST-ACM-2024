# zoi 展开与恢复重构方案（临时草案）

日期：2026-09-05  
阶段：方案已写，尚未改动实现。范围只限头文件跳板解析、钻石依赖去重、expand/restore 状态管理。

## 1. 已确认的问题

审查对象：F:\c++\my_code\HNIST-ACM-2024\scripts\zoi.ps1。

当前 expand 先保存 A.zoi.cpp，再原地写展开内容，A.zoi.sha 保存整份展开文件的 SHA1。第二次 expand 只要发现备份就失败；restore 只要发现整份文件有内容变化就跳过。因此：

1. 展开 → 新增 include → 再展开：被已有备份拦住。
2. 展开 → 改 solve 或新增 include → 恢复：整文件指纹不符，被当成“可能丢失修改”。
3. restore 跳过后，备份与指纹一直保留；用户只能强制丢弃修改或手动清理。
4. 去重表只存在于当次进程，当前输出注释不足以可靠重建 include 关系；直接删掉“备份存在”检查会把已展开代码当新源，造成嵌套展开和恢复链混乱。

隔离样例已复现：首次 expand 返回 0；新增头文件后第二次 expand 返回 1；restore 返回 1；两个旁置文件均残留。没有对真实题目执行恢复或清理。

**目录残留尚未确认来源。** 当前 zoi.ps1 本身只创建旁置文件，不创建存档文件夹。实施前应针对实际题目目录检查 status、VS Code 任务入口及遗留文件，区分 zoi 备份、安装备份与 .zoi-checks 测试目录，不混在一起删除。

## 2. 建议采用的方案

保留“原地展开、原文件测试、复制后直接交 OJ”的工作流，改成：

> 按生成块恢复 include，保留块外的题目代码修改；每次从恢复出的紧凑源码重新解析依赖。

不采用“在旧展开结果末尾继续补代码”，也不使用整文件差异猜测哪些修改属于用户。第一次实现不引入数据库、后台服务或通用三方合并器。

### 输出边界

只在根文件中每个被展开的 include 位置放一对机器可识别的 ASCII 注释：

    // zoi:begin <本次状态ID>:<块ID>
    ...这个 include 展开的依赖代码...
    // zoi:end <本次状态ID>:<块ID>

- 根文件本身不再被包成生成块；solve、main、题目自己的 Info/Tag 都保留在块外。
- 每个原始 include 都有记录，包括因钻石去重而未再次输出正文的 include；不能把原 include 一并遗忘。
- 状态文件记录块 ID、原始 include 原文、生成块指纹、解析出的依赖信息。
- ID 与状态文件配对，避免把用户普通注释误认成边界；成对解析，禁止用一个跨全文的贪婪正则截取。
- 检查生成块时规范化 LF/CRLF；输出保留根文件的换行约定。块外修改不参与冲突判定。

这是工具输出的标记，不是让竞赛模板增加运行期检查。

## 3. 三个命令的新语义

| 操作 | 预期行为 |
|---|---|
| 首次 expand A.cpp | 解析紧凑源码，生成依赖块和状态，再原地替换 |
| 展开后新增根级 include，再 expand | 回收未修改的生成块为原 include，保留新增 include 和题解修改，重新解析整个依赖图 |
| 未修改再 expand | 内容、依赖均未改变则不重写；仍可复制当前结果 |
| 依赖库内容变化后 expand | 从当前库重新生成，更新生成块；报告哪些依赖变化 |
| 修改 solve 后 restore | 只把生成块折回 include，保留 solve 修改 |
| 删除完整生成块 | 视为删除对应 include；后续重新展开时从剩余 include 重算共享依赖 |
| 修改了生成块内部 | 明确定位到该块，普通 expand/restore 不覆盖它 |
| 状态或标记损坏 | 报告缺失项并保留现场；不退回“强行覆盖旧备份” |
| 批量 restore | 每题独立处理、汇总成功/冲突/孤儿；一题冲突不妨碍其他题恢复 |

**首版明确边界：** 用户直接改了展开模板正文时，不保证自动回收为库引用。把修改静默扔掉会丢题目定制；把它写回模板库也不合适。首版将它列为真实冲突，并提供保留当前展开文件、仅解除管理的出口；“导出题目私有头文件”可后续独立设计。

新增 include 必须放在生成块外。若插入生成块内部，它属于模板块编辑，不能悄悄挪到根文件改变语义。

## 4. 钻石去重与跳板解析

解析层负责“这个 include 指向什么”，渲染层负责“在什么位置输出”。

- 搜索顺序先保持原约定：当前文件目录 → 仓库 zoi 目录 → 仓库根。
- 跳板名只用于定位；识别 make_stubs 生成的纯转发跳板，最终以模板母版的规范完整路径作为依赖身份。不能用短名或文件名去重。
- 目录边界、路径中的 . 和 ..、斜杠统一处理；Windows 按其路径大小写语义比较，Linux 保持大小写敏感。符号链接别名暂不承诺去重。
- 同一次生成重新建立 visiting 与 emitted 集合，分别表示递归链与已输出正文。正常有守卫的环状引用终止，无守卫递归包含报出依赖链。
- 标准库 include 保持原样；不是纯跳板的本地文件不擅自当别名穿透。
- 库内标准守卫模板在普通无条件引用区域去重；没有守卫、可能有意重复包含的文件不能一律按路径删掉。
- 条件编译中的 include 不能套用“全文件第一次遇到就算已输出”：例如 #if 0 中出现过 utils，不代表后面的无条件 include 可以删。首版对复杂条件或宏式 include 明确提示不支持，并在写入前停止；不假装实现完整 C++ 预处理器。标准头部 include guard 单独识别，不误判为复杂条件。
- 同名 include 多搜索位置仍按既有顺序解析，status 可显示实际目标，避免把另一份本地文件误当库模板。

去重目标是在保持编译语义的前提下减少重复正文；不是简单追求输出中“每个路径只能出现一次”。

## 5. 状态与清理

建议新格式仅使用题目旁的 A.zoi.state.json，不再长期同时维护 .zoi.cpp 与 .zoi.sha。

状态内容：格式版本、状态 ID、最近紧凑源码快照、生成块映射与指纹、依赖来源。写入过程中额外保存事务前后快照及摘要，提交成功后缩减为常态数据。

写入顺序：

1. 全部解析和冲突检查在内存完成，失败时不碰 A.cpp。
2. 同目录写待提交状态及新源码临时文件。
3. 替换源码，再提交状态；下一次启动能凭事务记录分辨“未替换／已替换但状态未提交”。
4. restore 成功后确认紧凑文件已写入，再删除本题状态和本次事务临时文件。

两个文件无法假设一次性原子更新，必须留下可恢复的中间状态；具体用 Windows/PowerShell 可验证的替换方式实现，不靠 try/catch 后一律删备份。

增加两个明确的管理出口：

- status <file|dir>：列出可恢复、模板块被改、源文件缺失、旧格式和孤儿状态；只读。
- forget <file>：用户明确放弃折回 include 时，保留当前展开文件，移除工具标记和本题有效管理状态。此后它就是普通自包含源码。未知、损坏状态不自动 forget。

源文件缺失时，备份可能是唯一副本，不自动清理。目录只在确认由本工具创建且为空时删除；不递归删除题目目录、不按宽泛的 *.zoi* 通配删除其他文件。正常恢复不留临时状态，真实冲突则说明保留原因和下一步。

## 6. 旧格式迁移

- 旧 .zoi.cpp + .zoi.sha 与当前源码完全对应：可先恢复到旧紧凑源码，再按新格式展开；迁移提交完成后清理旧文件。
- 旧展开源码已有修改：旧标记没有可靠的版本与块指纹，不自动猜测回收。保留源码和旧备份，status 明确标注旧格式冲突。
- 旧备份缺少指纹、源文件被重命名或缺失：独立报告，不让一次缺文件导致整个批处理无结论。
- 旧 -Force 保持“显式丢弃当前修改、恢复旧快照”的含义，不作为新默认路径；错误提示不把 Force 当作唯一解决办法。
- 临时存档目录的自动迁移/清理，要等核实实际创建者与命名后再定，当前方案不虚构其结构。

## 7. 验收用例

先建 scripts/zoi_check.ps1，用独立的小型假模板库测试，隔离题目文件并禁用测试时的剪贴板副作用。

- [ ] A→B/C→D：D 正文只输出一次，restore 后原来的两条 include 均保留。
- [ ] 首次展开 → 增加头文件 → 再展开 → 改 solve → 恢复：新增依赖与 solve 修改都保留。
- [ ] 连续展开无变化：字节稳定，不积累套娃注释、状态或临时文件。
- [ ] 根文件原有注释、空行、include 顺序与重复 include 能恢复。
- [ ] 删除完整依赖块后重建：剩余依赖仍能得到共享底座。
- [ ] 生成块内部被改、标记缺失/重复：不覆盖当前代码，能定位具体冲突。
- [ ] 库模板发生变化：重新展开更新库内容，但不吞题目代码。
- [ ] . / .. 路径别名、同名不同文件、纯跳板与直接母版引用。
- [ ] 标准守卫环、无守卫环、复杂条件 include：分别符合支持边界。
- [ ] 旧格式未改/已改/缺 sha/缺源文件，批量混合状态。
- [ ] 写状态后、替换源码后分别注入失败：能继续或回收，不静默丢源码。
- [ ] 正常 restore、明确 forget 后只清理本题状态，其他题目与孤儿备份不受影响。
- [ ] Windows PS5.1 与 PS7；中文/空格路径、CRLF/LF。
- [ ] GCC C++20 编译并运行：紧凑态与展开态结果一致；真实库抽样 seg+bit、HLD+seg 等共享底座组合。
