# 对拍现状

[看口语概览](status.md) · [看 AI 验证明细](details.md) · [原始测试资产关系](../../rules/reliability.md)

口语概览回答每个模板现在测得怎样, 还要注意什么. AI 明细保留模板与套件、API、独立暴力、边界用例、运行环境、结果和指纹. 两张表同源生成, 不分别手填.

## 平时怎么用

```powershell
./scripts/run_checks.ps1 -Filter conn
./scripts/make_verification.ps1
```

第一条编译运行, 自动写入证据并更新两张表. 第二条不跑测试, 只根据现有证据和当前源码重算状态. 修改源码后需要运行第二条或重新对拍, 静态 Markdown 不会自行刷新.

- 测试范围登记在 `rules/verification.json`: 按模板和套件逐项写 API、独立参照、用例、口语摘要和限制. 没核实的模板保持未登记, 不从 include 猜覆盖.
- runner 自动写入 `records/verification/runs/*.json`: 每次一个记录, 保存时间、编译器、参数、退出结果及源码/依赖清单指纹. 可以随代码提交以便其他人查阅, 不手填通过状态.
- 原始日志保存在 `.zoi-checks` 或指定 ReportDir, 不提交. JSON 中的本地日志位置只在保留现场的电脑上存在, 删除日志不等于删除历史运行事实.
- CI 将本次证据和两张表写入各自 ReportDir, 随现有 artifact 上传, 不自动提交仓库. 下载后可将 `verification-runs` 中 JSON 放入 `records/verification/runs`, 再运行生成器合并各环境结果. 只导入可信 runner 产物.
- 普通回归与 sanitizer 分开记, Windows 与 Linux 分开记. 同套件同环境同检查方式只展示最新记录; 最新失败不会被旧通过盖住.
- 编译器版本和完整参数随记录展示. 系统头文件不做内容指纹, 不保证不同系统库环境等价.

## 什么时候需要重验

源码、测试、传递的本地 include、runner 或范围登记变化, 指纹不匹配就标待重验. CRLF 与 LF 归一化, 其余内容包括注释变化保守视作变化. 条件 include 的两侧都计入; 宏 include 保守纳入全算法源码. 运行前后各取一次指纹, 检测到中途变化则不当作当前通过.

`verification.json` 整份文件参与指纹, 调整其他条目的登记也可能使旧记录待重验. 这是保守策略, 不靠推断自动继承旧通过.

没有结构化指纹的老日志仍可在历史记录中查阅, 不补造当前通过. 本轮先登记已详细核实的连通性四件套, 其余模板明确显示覆盖未登记. 学习进度独立, 不因对拍通过变成已掌握.

## AI 维护顺序

1. 修改模板、依赖或测试前, 从明细和测试代码确认相关 API 与缺口, 不以套件数量判断充分性
2. 修改或新增测试时更新范围登记, 保留未覆盖项
3. 跑相关套件, 检查自动生成的两张表及失败日志; 暂不运行时执行 make_verification 刷新待重验状态, 不沿用旧绿灯
4. 提交时一起纳入登记、真实证据和生成表; 原始临时日志不提交

新表系统自检: `./scripts/check_verification_test.ps1`
