# 对拍现状

[看口语概览](status.md) · [看 AI 验证明细](details.md) · [原始测试资产关系](../../rules/reliability.md)

查某次规模补验、缺陷修复和已知限制, 从 [专项验证索引](../../records/verification/README.md) 进入对应报告。

口语概览回答每个模板现在测得怎样, 还要注意什么. AI 明细保留模板与套件、API、独立暴力、边界用例、运行环境、结果和指纹. 两张表同源生成, 不分别手填. 模板行只收 catalog 中正式登记的引擎, 不收例题、临时题解、笔记或其他豁免代码; 按登记身份筛选, 不靠 CF / 洛谷文件名猜测

## 平时怎么用

```powershell
./scripts/run_checks.ps1 -Filter conn
./scripts/make_verification.ps1
```

第一条编译运行, 自动写入证据并更新两张表. 第二条不跑测试, 只根据现有证据和当前源码重算状态. 修改源码后需要运行第二条或重新对拍, 静态 Markdown 不会自行刷新.

- 测试范围登记在 `rules/verification.json`: 按模板和套件逐项写 API、独立参照、用例、口语摘要和限制. 没核实的模板保持未登记, 不从 include 猜覆盖.
- runner 自动写入 `records/verification/runs/*.json`: 每次一个记录, 保存时间、编译器、参数、退出结果及源码/依赖清单及分项范围指纹. 可以随代码提交以便其他人查阅, 不手填通过状态.
- 原始日志保存在 `.zoi-checks` 或指定 ReportDir, 不提交. JSON 中的本地日志位置只在保留现场的电脑上存在, 删除日志不等于删除历史运行事实.
- CI 将本次证据和两张表写入各自 ReportDir, 随现有 artifact 上传, 不自动提交仓库. 下载后可将 `verification-runs` 中 JSON 放入 `records/verification/runs`, 再运行生成器合并各环境结果. 只导入可信 runner 产物.
- 普通回归与 sanitizer 分开记, Windows 与 Linux 分开记. 同套件同环境同检查方式只展示最新记录; 最新失败不会被旧通过盖住.
- 独立目标规模/深链作业的 `stress-*` 附件使用专门的 summary.json, 记录 profile、压力参数、栈限制、依赖哈希及 STACK_LIMIT. CI 分别运行 lca-vt 和 completed-graph, 后者所有压力项必须通过, 不接受 STACK_LIMIT. 它不是 runner 的 records/verification/runs 格式, 不直接导入两层表; 当前表仍只显示 runner 无参数套件的结构化结果, 压力范围另查附件和[测试说明](../../scripts/checks.md).
- 编译器版本和完整参数随记录展示. 系统头文件不做内容指纹, 不保证不同系统库环境等价.

## 什么时候需要重验

“指纹”是内容的 SHA-256 校验值，用来判断上次测试之后内容有没有变；相同只表示内容相同，不等于算法必然正确。

新版将两类变化分开判断：

| 变化 | 哪些结果需要复验 |
|---|---|
| 对拍代码、它引用的模板或传递本地依赖 | 使用该套件的结果 |
| runner、进程执行、资产扫描或校验实现 | 受这些执行脚本影响的套件 |
| 某个模板在某个套件下的 API、独立参照、用例或限制 | 仅这个“模板＋套件”条目，其他模板的登记不连带失效 |
| 新增范围登记 | 新增条目不能沿用登记前的通过结果 |
| 修改口语摘要 summary、JSON 缩进/属性顺序、登记条目顺序、API/用例列表顺序 | 不需要复验，重新生成表即可更新文字 |
| 与该套件无关的源码或范围登记 | 不影响原结果 |

源码仍只统一 CRLF/LF，包含注释的其余改动保守视作变化。条件 include 的两侧都计入；宏 include 无法确定目标时，保守纳入全算法源码。系统头文件不做内容指纹，环境与编译参数在运行记录中单独展示。

运行前后分别检查源码与各条范围。如果运行期间只有 A 的范围变化，A 待复验，B 的稳定范围仍可使用；源码变化则整个套件不能作为当前通过。明细按模板列出范围状态，另列套件运行结果、具体复验原因和变化文件。最新失败不会被更早的通过替代，语法检查也不会覆盖回归结果。

证据 JSON 外层仍为 schema 1，新结果带 `fingerprintVersion: 2`：`fingerprint/files/stable` 对应套件源码和执行脚本，`scopes` 保存每个模板的范围校验值与运行期间稳定性。范围由 template、suite、api、oracle、cases、limitations 六个字段规范化计算，summary 只作显示。修改这套计算规则时须考虑版本兼容，不能直接把旧证据改写成新证据。

旧版记录没有保存分项范围，显示“旧版记录，需新版复验”，历史退出结果和时间仍保留。下一次真实对拍后自动展示新版记录；不修改旧 JSON、不忽略缺失信息强行恢复绿灯。

没有结构化指纹的老日志仍可在历史记录中查阅, 不补造当前通过。登记范围按工作板逐件扩展,
当前范围查生成表, 未登记项仍显示未知。学习进度独立, 不因对拍通过变成已掌握。

## AI 维护顺序

1. 修改模板、依赖或测试前, 从明细和测试代码确认相关 API 与缺口, 不以套件数量判断充分性
2. 修改或新增测试时更新范围登记, 保留未覆盖项
3. 跑相关套件, 检查自动生成的两张表及失败日志; 暂不运行时执行 make_verification 刷新待重验状态, 不沿用旧绿灯
4. 提交时一起纳入登记、真实证据和生成表; 原始临时日志不提交
