## 怎么填

- **本人学习进度**：未开始、正在学、学过待复习、已掌握、暂不学；不知道就保留“待确认”。学习状态由本人确认，或依据明确的本人记录填写并注明出处。不能从文件存在、代码漂亮或测试通过反推。
- **库内整理状态**：仅目录骨架、仅占位、已有笔记、旧实现待整理、整理中、已登记跳板；初判旁保留证据。这里“已登记跳板”不代表质量合格，接口和边界审查仍另查。
- **判断依据与下一步**：说明文件里有什么、为什么这么判断；本人确认后补一句下一步，例如“学过，旧版待整理，先补多测复用”。旧实现只有明确历史证据才这样标，代码风格差异不够。

本轮发现的确切线索：字符串、图论、数学等家族 README 有学习路线，数学部分写“从零开始”；catalog 中多数笔记条目只有“占位：待入库”，矩阵树定理有正文。个人 records/whf 目前只有目录说明，没有逐项学习记录。因此初表没有擅自标任何一项为“已掌握”或“未开始”。

## 维护约定

这是一份可直接修改的进度账，不是运行生成器就覆盖的报告。你可以直接说“某某学过但模板旧”“某某还没开始”，AI 修改对应行并记录依据即可。后续增加或撤下模板、知识点时只增删对应行，保留既有学习确认，摘要数量随之更新。
相同知识点的不同实现暂分别列出，避免把其中一个学过误算成全家都会；本人确认适用整个家族时可批量更新。
想暂不学习的项目明确记“暂不学”，不要删掉唯一记录。旧 README 的推荐顺序不替你决定现在的学习计划。

没有正文文件的本地目录只记名称、不放失效链接；即使 Git 不保存空目录，这些学习目标仍保留在表中。

## AI 何时询问、如何同步

本节是学习进度同步的唯一行为正文，适用于所有 AI。只查本次涉及的知识点，不把整个进度表变成每次开工的问卷。

| 触发场景 | 应做的事 |
|---|---|
| 开始讲解、陪练或接手某个旧模板 | 先查对应行。状态待确认或用户描述与旧记录不一致时，在安排讲解深度前简短询问：“这部分你没学过，还是学过需要复习？” |
| 建成新模板、整理完旧模板 | 收尾时按文件和验证结果更新库内整理状态；学习状态仍未知或本次确实开展了学习时，主动提一句是否更新学习进度，例如“模板已整理好，你这部分现在是正在学，还是学过待复习？” |
| 用户明确说“学过”“不会”“没开始”等 | 按上下文更新对应学习状态，不为同一信息再问一次；表述不足以区分状态时只澄清差异。一次会话的“懂了”不自动等于已掌握整个家族。 |
| 新增、重命名、移动或撤下模板/知识点 | 同步进度行、源码链接及方向摘要。重命名/移动要迁移原学习确认；撤下代码保留学习记录并注明现状，不把记录一起删除。 |
| 单纯跑测试、修脚本、改注释或排版 | 不例行询问学没学过；只有涉及条目变化或出现新的用户陈述时才同步。测试通过不能提升学习状态。 |

- 已有明确确认且没有新变化时不重复询问；一次只问当前相关项目，用户明确讨论整个家族时才批量确认。
- 用户不回答就保留原学习状态，若已经问过，在该行依据栏记“日期：已询问，待回复”；不因沉默认定已学，也不在同一工作中反复追问。以后用户重新开展该主题学习或主动提起时再确认。用户说暂不记录时记明偏好并停止追问，直到用户改变要求。
- 未回复不阻塞已经授权的代码整理、验证与客观入库状态同步。用户已明确提供状态，就直接记，不再额外征求“是否允许记表”。
- 更新学习状态时，在“判断依据与下一步”保留简短证据：日期、用户确认内容及适用范围；旧路线只能作线索，不冒充本人确认。
- 模板工作结束前核对：对应行存在、名称/链接有效、库内状态符合实际、原学习确认未丢、收到的新确认已落表。若无变化，说明无需更新即可，不制造空改动。需要本人确认的项如实保留，不以“表已同步”掩盖未知状态。
- 这份进度表手工维护；make_features 与 make_reliability 只生成各自目录，不覆盖学习记录。新增模板还需按维护流程更新 catalog、跳板与生成目录，学习表不能代替这些步骤。
