# 协作与执行约定

适用于所有 AI 和维护者。算法契约见 rule.md，工具指南见 docs/README.md。用户明确要求优先；历史记录不自动成为新规则。

学习询问与模板收尾同步执行 [进度表约定](../docs/progress/README.md#ai-何时询问如何同步)；所有模型使用同一份记录，不另建私有学习状态表。

验证同步执行 [两层表维护顺序](../docs/verification/README.md#ai-维护顺序); 用户概览与 AI 明细不分别手填, 个人学习状态仍只按用户确认

功能变更收尾统一执行 [rule 双向同步要求](../rule.md#适用范围与阅读顺序), 同时核对给 LLM 的规则与给用户的功能表; 不以工作历史或验证表代替功能说明。

## 范围与交接

- 一次处理一个明确范围；开始前查看工作板，标明执行者和涉及文件。不要修改其他人的进行中范围，不整库加锁。
- 角色按本次任务分配，不绑定模型。提交前检查 git status，只纳入已授权且属于本次范围的改动，不吞他人半成品。
- 同一文件有未合流分歧时，在工作板写明两案与依据，请用户裁决，不覆盖对方成果。
- 工作板只留待办、进行中、待裁决和有效交接；完成项连同证据移入 sweep-history.md，再移出工作板。
- 区分模板修改、测试补强和套件运行；记录日期、范围、环境、参数、结果与日志，有提交号就附，没有就写未提交。
- 他人代记不等于亲自验证；误记要更正，原记录留在历史。代码或依赖变化只重验受影响项，不重复扫描未变化且已验证范围，也不把旧绿灯套给新改动。
- 暂停时写明下一步、已知失败和日志位置，解除已结束的领取；恢复先看工作板。

下列交互与终端条款从原 rule.md 原文迁入，编号暂保留以便核对。

## 1. 交互纪律 (每条都是踩过的坑)
1.1 交代码交整份, 可直接入库。禁止只给片段或"省略不变部分"。
1.2 每次改动附清单: 改了哪里、为什么改。用户不做人工 diff。
1.3 新引擎/新接口要带三样: 接口注释(返回值约定+时空复杂度)、
    尾部 Usage 示例、对拍验证代码。
1.4 有分歧就给一个明确裁决(说清代价), 让用户拍板或照办。
    不要摆一堆选项让用户自己挑。裁决错了要认。
1.5 外部建议/警告要逐条审: 诊断和药方分开判断。历史上有过
    "诊断对、药方错"的警告, 病灶和药必须一起审。
1.6 判死因(TLE/MLE/RE)要给数字: 内存多少字节、结点几个、时间花在哪。
    "可能是性能问题"这种话不合格。
1.7 不确定就说不确定。引用平台行为(评测机波动等)必须是公认事实。
1.8 启发式小件的机制可用短注释说明, 但本轮现役模板最终验证不因代码短或性质可自证而免验;
    具体范围、独立参照与目标规模按 rule.md 第 9 节执行, Usage 不代替验收。

## 工作区与沉淀

- 本项目人工/AI 临时脚本、编译副本、预览和下载工具放库内 `.zoi-checks/codex-work/`,
  按任务建子目录; runner 自建 `.zoi-checks/` 隔离目录, 报告在 `.ci-results/`。这些均不提交。
- 命令从库根执行。编译子进程的 TEMP/TMP/TMPDIR 指向库内对应任务目录,
  使用已有 Invoke-CheckProcess 或压力入口; 不改系统全局环境, 不把本项目中间产物放 C 盘会话目录。
- 临时工作区不是长期记忆: 当前任务/下一步/未决问题写 sweep-board, 完成与证据移入 sweep-history;
  通用约束写现行 rule/对应规则, 用户能力说明写 docs/features, 详细专项证据写 records。
  不新建另一份竞争的长期任务表, 不只把结论留在忽略目录或聊天里。
- 接手先读入口和工作板, 按需追溯记录; 收尾检查任务状态、两类说明、证据链接与未决问题。
  新版测试入口按完成标记保留每类最近三份成功现场, 失败和人工工作区不自动清理; 操作见 docs/maintenance。
  清临时产物前确认所需证据已沉淀, 移动旧现场先核对文件清单和哈希; 不猜删来源不明的文件。
  该约定只管理本库工作产物, 不改变 Codex 自身日志、缓存或 WSL 的系统存储位置。


## 12. 终端执行规范 (违反 = 会话锁死或产出污染)
12.1 禁止交互式命令: less/more/vim/nano/top 这类要人按键才能退的
     一律禁。AI 会话的 shell 没有 stdin 可喂, 进交互态只能人工杀进程。
12.2 git 输出禁分页: git log/diff/show 一律写 git --no-pager <子命令>。
     不赌 core.pager 配置, 默认 pager 弹出来就是锁死(踩过)。
12.3 看文件用 cat/head -n/tail -n 或读文件工具, 不用任何会接管
     终端的编辑器。
12.4 Windows 命令行:
     - 连接符看宿主: cmd/PS7+ 用 &&(失败即停); PS 5.1 的 && 是语法
       错误, 只能用 ; 或拆开多次调用。不确定宿主版本就别写 &&。
     - 路径带空格/中文必须双引号(F:\c++\my_code\... 不加引号会被
       空格截断)。
     - PS5.1 没有 < 重定向(保留字), 要给程序喂 stdin 文件, 用
       cmd /c 包裹。
     - PS5.1 对程序的 > 重定向默认写 UTF-16LE+BOM+CRLF, 再喂回给
       程序读必炸(\0 会把数字切碎; i128 对拍那次假故障, -1 读成 0,
       一度冤枉了模板库)。要字节保真, 一律
       cmd /c "exe < in > out" 整体包裹, 别让 PS 碰字节流。
12.5 git 写操作要授权: push 等用户明说; 说了一次 push, 就可以
     git add . + commit + push 一气呵成, 不用再分步请示。零碎小改
     (rule 措辞类)攒在工作区, 跟下次实质改动合推, 不单独开 commit。
     (教训: §12 入宪那次, 没经授权 add/commit/push 三连, 被用户封堵。)
12.6 commit 信息要像人写的: 一行动词+对象。禁破折号轰炸、禁罗列、
     禁中英混排装饰、禁自造压缩词和营销腔("五查""直达"这种词是
     AI 发明的, 人只会说"加xx检查""修xx")。
     对: "补终端执行规范"。错: "rule: §12 终端执行规范——禁交互式
     命令/git --no-pager/..."。
12.7 命令超时或输出捕获失败时: 副作用可能只生效了一半, 恢复后
     必须先对账实际状态(数文件、抽内容)再继续, 禁止假设成功也禁止
     假设失败(实测: 删旧跳板生效了, 重新生成没跑, 留下 30 处烂账)。
     终端输出彻底读不到时, 改走日志中转: cmd /c 把命令输出落日志
     文件, 再用读文件工具看——绕开终端捕获层。
